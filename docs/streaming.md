# Phase 04 청크 스트리밍

C# / .NET 10, Raylib-cs / OpenGL을 유지한다. 기존 [저장 형식](storage.md)의 v4 청크 파일을 재사용하고, 월드 전체를 한 번에 메모리에 올리는 경로와 플레이어 주변만 유지하는 경로를 구분한다. 낙하 블록은 [falling-blocks.md](falling-blocks.md)를 따른다.

## 좌표와 생성

World.CreateStreaming(seed, registries)는 스트리밍 월드를 만들고 WorldStreamer가 필요한 열을 불러온다. ColumnCoord는 X/Z 청크 좌표이며 한 열의 기본 생성 범위는 Y=0–63, 즉 16³ 청크 네 개다. 새 블록 설치 범위는 Y=0–255다.

StreamingTerrainGenerator.Version은 2다. Generate(seed, coord, cancellationToken)는 독립적인 Block[4096]을 반환하며 World·입력·GPU에 접근하지 않는다. 노이즈는 전역 좌표와 시드로 계산한다. 나무는 경계를 넘어 닿을 수 있는 이웃 뿌리도 평가하고 전역 우선순위와 줄기 우선 규칙을 적용하므로 청크 생성 순서가 수관을 바꾸지 않는다. GetBlock과 SurfaceHeight는 같은 전역 필드의 좌표 조회다. 스폰 근처는 높이 9의 평지다.

저장 Cell은 signed int이며 청크 원점이 int에 들어오는 범위만 허용한다. 플레이어와 낙하 블록은 float 좌표의 정밀도를 고려해 현재 X/Z 약 ±1,000,000블록 범위에서 동작한다. 저장 좌표 범위가 모든 좌표에서 같은 렌더링 정밀도를 보장한다는 뜻은 아니다.

기존 유한 월드는 현재 청크의 블록과 편집을 보존한 채 스트리밍을 켤 수 있다. 이미 알려진 열은 재생성하지 않는다. 새 영역에는 v2 생성기를 적용하므로 과거 생성기의 가장자리와 새 영역 사이에는 절벽이나 높이 차이가 생길 수 있다. 구형 월드 전체를 새 지형으로 덮어쓰는 마이그레이션은 하지 않는다.

## 소유권과 작업 흐름

WorldStreamer.Update(player, radiusChunks)는 월드 소유 스레드에서 호출한다. 플레이어 중심 정사각형 안의 열을 거리 제곱 우선순위로 요청한다. 기본 radiusChunks는 2이며 API 허용 범위는 0–8이다. 실제 게임은 표시 거리 설정과 연결할 수 있다.

| 작업 | 실행 위치 | 기본 예산 |
|---|---|---|
| 저장 청크 읽기·검증 또는 새 지형 생성 | 백그라운드 Task | 동시에 최대 2개 열 작업 |
| 완료된 열의 World 반영 | 소유 스레드 | 프레임당 최대 1개 열 |
| 저장할 Dirty 청크 스냅샷 캡처 | 소유 스레드 | 프레임당 최대 2개 청크 |
| 먼 열 해제 | 소유 스레드 | 프레임당 최대 1개 열 |
| CPU 메시 생성 | 백그라운드 ChunkMeshScheduler | 동시에 최대 2개 청크 |
| GPU 버퍼 갱신·해제 | 렌더링 스레드 | 렌더러 업로드 예산 적용 |

StreamingOptions는 MaxLoadJobs, MaxIntegrationsPerFrame, MaxUnloadsPerFrame, MaxSaveCapturesPerFrame, UnloadMargin, MaxResidentColumns를 제공한다. 기본 언로드 여유 반경은 1개 열, 상주 열 상한은 256개다. 이 상한에는 알려진 빈 열도 포함한다. 보존해야 하는 낙하 열과 작업이 상한을 채우면 추가 로딩을 기다린다.

로딩 작업은 호출 시점의 저장 참조·시드·동결 Registry를 받는다. worker는 라이브 월드 컬렉션을 읽거나 변경하지 않는다. 플레이어가 요청 범위를 벗어나면 취소하고, 완료된 작업도 아직 필요한 열인지 소유 스레드에서 다시 검사한다. 취소한 작업을 실제 완료 전에 목록에서 지우지 않아 작업 개수 상한을 지킨다. 실패는 LastError에 남고 같은 열은 대기 후 재시도한다.

## CPU 메시와 GPU 자원

ChunkMesher.Capture(world, coord)는 소유 스레드에서 18³ 블록 halo, 램프 전원과 회로 위치를 복사한다. ChunkMeshSnapshot의 배열은 외부에 노출하지 않으며 메타데이터는 동결된 BlockRegistry를 공유한다. Build(snapshot, greedy, cancellationToken)는 이 스냅샷만 읽어 CPU 메시를 만든다. 기존 Build(world, coord)도 동기 검증 경로로 남아 있다.

ChunkMeshScheduler.Request는 청크 객체·메시 리비전·수명주기 작업 토큰을 함께 보관한다. CancelObsolete와 TryTakeCompleted는 편집, 이웃 경계 변경, 월드 교체, 언로드와 청크 재생성으로 오래된 결과를 거부한다. 취소한 worker도 완료·예외를 관찰할 때까지 예산에 포함한다.

CPU 완료만으로 Ready 상태가 되지 않는다. 렌더링 소유자가 GPU 업로드에 성공한 뒤 CompleteMeshing(token)을 호출한다. 업로드 실패는 Fail, 결과 폐기는 Cancel로 해당 작업을 끝낸다. 창·GL 컨텍스트가 닫히기 전에 worker를 취소·관찰하고 GPU 캐시를 해제한다. 표시 거리와 프러스텀은 그리기 및 요청 우선순위에 쓰며, GPU API를 worker에서 호출하지 않는다.

## 저장 후 해제와 재진입

먼 열에 Dirty 청크나 삭제 tombstone이 있으면 먼저 저장을 요청한다. StreamingSaveSession은 청크 콘텐츠 세대와 팔레트 데이터를 프레임별로 캡처하고, 분리된 저장용 월드에 메타데이터와 낙하 상태를 함께 복사한다. 백그라운드 작업은 이 분리된 상태만 직렬화하고 파일을 커밋한다.

저장 영수증은 원래 콘텐츠 세대와 함께 돌아온다. 소유 스레드는 같은 세대만 MarkSaved하므로 캡처 뒤 발생한 편집은 계속 Dirty로 남아 다음 저장을 기다린다. 실패한 저장은 LastError를 보고하며 Dirty 열을 해제하지 않는다. 정상 저장 후에만 메모리 청크를 Evict하고 렌더러가 해당 GPU 캐시를 해제한다. 활성 낙하 블록이 사용하는 열은 고정하여 중간 상태를 잃지 않는다.

v4 매니페스트에는 다음 정보를 추가한다.

| 필드 | 의미 |
|---|---|
| IsStreaming | 스트리밍 월드 여부 |
| GenerationVersion | 새 영역의 지형 생성 버전 |
| KnownColumns | 생성·방문한 열; 블록이 없는 상태도 보존 |
| FallingBlocks | 활성 낙하와 대기 후보 상태 |
| Chunks | 현재 메모리에 없는 청크도 포함한 영구 파일 참조 |

KnownColumns에 있는 빈 열은 로드 시 빈 상태로 복원한다. StoredChunkReferences는 언로드된 청크의 파일을 계속 참조하므로 이후 다른 열을 저장해도 멀리 있는 편집이 사라지지 않는다. 로딩 중 참조한 파일은 RetainedChunkFiles로 보호해 저장 정리가 worker의 입력 파일을 먼저 지우지 않게 한다.

명시적인 저장·종료는 FlushSaves로 대기 저장을 관찰하고 현재 상태를 마저 저장한다. 단일 파일 ExportSnapshot은 언로드된 저장 청크도 모아 내보낸다. 기존 v1/v2/v3 읽기와 원본 백업, v4 체크섬·복구 규칙은 유지한다.

## 입력과 현재 한계

미로딩 열은 이동·낙하에 빈 공간으로 간주하지 않는다. IsCellAvailable이 거짓인 셀은 충돌 경계가 되고, 착지나 낙하는 해당 열이 준비될 때까지 기다린다. 음수 좌표에서도 플레이어 충돌·시점·설치를 같은 전역 좌표로 처리한다.

예산은 처리 개수의 상한이며 모든 프레임의 시간을 보장하는 밀리초 제한은 아니다. 스냅샷 캡처·완료 반영·분리 저장 상태 준비에는 소유 스레드 작업이 남아 있다. 명시적 로드·저장과 종료 대기는 동기 작업을 포함한다. 최대 반경·다수 편집·대량 낙하의 실제 비용은 벤치마크와 장시간 검증 기록으로 판단해야 한다.

청크 개수와 실제 메모리, 디스크 공간은 유한하다. 높이·실용 좌표 제한·상주 상한을 벗어나는 확장은 별도 설계가 필요하다. 다른 Phase의 몹·유체·날씨가 이 스트리밍 단계에서 구현된 것은 아니다.

## 현재 게임 연결과 추가 경계

실제 Game은 새 월드부터 스트리밍을 사용하고, 구형 v4는 참조를 지연 로드한다. 현재 게임은 최대 상주 열512개를 허용하며 API 기본값은256개다. 메모리 압력에서는 언로드 여유 반경을 줄여 플레이어 중심 열을 먼저 확보한다. 로드·저장 오류는 game.log와 화면 알림으로 전달한다. GPU 업로드는 실제 렌더 스레드에서 프레임당 최대2청크로 제한하며 CPU 작업 스레드에서 호출하면 거부한다.

자동 저장 주기는 렌더 프레임 수가 아닌20TPS의200틱이다. 저장 포즈는 yaw/pitch까지 보존한다. 플레이 범위 밖의 구형 Y참조는 파일에 보존하고 거주 메모리로 불러오지 않는다. 저장된 한 열의 읽기 바이트는 기본16MiB로 제한한다. 미로딩 저장 청크의 직접 수정을 거부하므로 나머지 저장 셀이 덮어써지지 않는다.

명시적 Save/Load/내보내기·최종 Flush는 동기 완료할 수 있다. 창을 닫거나 세션을 바꾸기 전에 작업을 취소·관찰하여 오래된 완료가 게시되지 않게 한다. 검증 수치와 실제 측정은 [Phase04 검증 기록](validation/phase04/README.md)에 보존한다.
