# IP 직접 접속 멀티플레이

Phase05 인벤토리·제작 위에 추가한 같은 버전용 직접 접속 기능이다. 외부 라이브러리 없이 .NET10 TCP를 사용한다. 호스트가 현재 월드의 저장과 시뮬레이션을 소유하고, 참가자는 별도 월드 복제본을 표시한다.

## 호스트와 참가

1. 호스트는 공유할 월드를 연 뒤 **F8**을 누른다.
2. 이름과 포트(기본 **25565**), 필요하면 공유 비밀번호를 입력하고 **HOST**를 선택한다.
3. 참가자는 F8에서 호스트의 IP 또는 DNS 주소, 같은 포트·비밀번호와 이름을 입력하고 **JOIN**을 선택한다.
4. 같은 PC의 두 번째 실행으로 검사하려면 주소에 `127.0.0.1`을 쓴다. 서로 다른 PC가 같은 LAN에 있으면 호스트 PC의 LAN 주소를 쓴다.
5. 참가를 끝내려면 F8의 **LEAVE**를 선택한다. 호스트가 종료되면 참가 연결도 종료된다.

이름은 출력 가능한 ASCII 최대24자다. 호스팅은 현재 월드를 유지하며, 참가 전에 기존 개인 월드를 저장·flush한다. 연결·초기 동기화가 완료될 때까지 개인 월드를 바꾸지 않는다. 실패·취소 시 개인 월드는 그대로 남고, 참가 후 LEAVE하면 원래 월드 객체와 위치·시점을 복원한다. 참가자의 복제 월드를 개인 `world.json`에 저장하지 않는다.

참가 중 개인 월드 저장/불러오기·새 월드 생성은 막는다. 호스트는 저장할 수 있지만 공유 중 불러오기/새 월드 전환은 막는다. Esc나 F8 화면은 공유 시뮬레이션을 멈추지 않는다. 인벤토리 창은 자신의 이동을 멈추며, 호스트의 20TPS 월드 계산은 계속 진행한다.

호스트 PC까지 연결 가능한 TCP 경로가 필요하다. 인터넷 접속은 사용자가 해당 포트의 네트워크/공유기 설정을 구성해야 한다. 프로그램은 방화벽·공유기 설정을 바꾸지 않는다. 친구 초대·로비·계정 서비스·NAT 중계·전용 서버 서비스·TLS는 구현하지 않았다. 공유 비밀번호는 이 버전의 접속 제한이며 암호화된 인증 체계를 대신하지 않는다.

## 동기화와 권한

연결 시 프로토콜 버전과 등록 콘텐츠/레시피 지문을 비교한다. 맞지 않는 클라이언트는 월드를 교체하기 전에 거부한다. TCP 수신/송신 작업은 바이트와 JSON만 다루며, 실제 월드·인벤토리·회로 변경과 GPU 작업은 기존 소유 스레드에서 수행한다.

참가자의 블록 설치·채굴·레버 조작은 명령으로 호스트에 전송한다. 호스트가 위치·사거리·로드 상태·아이템/슬롯·수량을 확인하고 결과를 보낸다. 슬롯 이동·분할·드래그·Shift 이동·제작·버리기도 인벤토리 대체 JSON이 아닌 의도로 전송한다. 단조 증가 요청 번호로 이미 처리한 명령의 중복 실행을 막는다.

플레이어마다 자신의 인벤토리·제작 입력·커서를 가지며 다른 플레이어의 소지품을 바꾸지 않는다. 호스트의 플레이어 기록은 개인 접속 프로필의 해시로 저장한다. 클라이언트 프로필은 로컬 `multiplayer-profile.json`에 보관하고 공개 아바타 ID와 분리한다. 새 프로필은 기존 샌드박스의 시작 재료를 받으며, 같은 프로필로 재접속하면 호스트가 저장한 소지품을 복원한다. 월드당 보존 프로필은 최대128개다.

공유 월드는 청크별 데이터와 명시적인 삭제 상태를 전송한다. 늦게 접속한 플레이어도 수정된 블록을 받는다. 플레이어 위치·시점, 회로 전원, 낙하 블록, 버린 pickup을 갱신한다. 클라이언트는 독립적으로 중력·제작·청크 저장을 확정하지 않는다. 플레이어 이동은 클라이언트에서 표시하고 호스트가 유한 범위·이동 속도·충돌을 제한한다. 완전한 서버 물리 예측/재조정이나 전문적인 치트 방지 체계는 아니다.

스트리밍은 호스트 주변과 참가자 관심 위치를 고려한다. 참가자의 로드 반경은 호스트 반경과 반경2청크(최대5×5열) 중 작은 값으로 제한한다. 새 열 생성·통합·저장과 GPU 업로드 예산은 기존 스트리밍 계약을 유지한다.

## 네트워크 자원 한도

와이어 형식은 4바이트 big-endian JSON 본문 길이와 UTF-8 `{Type,Sequence,Data}`다.

| 항목 | 한도/동작 |
|---|---|
| 한 프레임 | 최대8MiB, 길이 확인 후 본문 할당 |
| 연결별 송·수신 큐 | 각각 최대128메시지 및16MiB |
| 동시 접속 | 호스트 외 참가자 최대8명, 초과 연결 거부 |
| 접속 대기 | 최대10초 및 취소 지원 |
| 잘못된 입력 | 불완전/중복 필드·잘못된 JSON·음수 번호·초과 길이를 거부하고 해당 연결 종료 |
| 느린 연결 | 큐 예산을 넘으면 연결 종료, 월드 스레드에서 송신 대기하지 않음 |
| 종료 | 소켓 종료·취소·백그라운드 작업 완료를 관찰 |

TCP 메시지가 여러 조각으로 나뉘어 와도 완성된 프레임만 게시한다. 클라이언트가 과거 명령을 다시 보내도 소지품이나 월드 변경을 반복 적용하지 않는다. 저장과 복제의 소유권을 나누어 접속 실패가 기존 개인 저장을 덮어쓰지 않게 한다.

## 검사와 측정

`--multiplayer-tests`는 외부 서비스 없이 실제 loopback TCP와 호스트/참가자 세션을 사용한다. 프레임 분할·Unicode/Vector3·잘못된 프레임·큐/접속 한도·취소/폐기, 호스트와 두 참가자의 초기/늦은 접속·변경 승인·거부·중복 요청·소지품 분리·재접속·저장 보존을 검사한다. 서버에서 검증하는 3×3 제작·제작대 접근, 단일 배치의 잘못된 핸드셰이크 후 재시도, 작은 위치 패킷 연속 전송의 누적 이동 예산, 원격 관심 열의 저장·언로드·재접속도 포함한다.

`--multiplayer-benchmark`는 준비20회 후 4096셀 청크와 확인 응답을200회 실제로 주고받고 양쪽 데이터를 검증한다. JSON·작업 스케줄·1ms 소유자 폴링을 포함한 loopback 경과 시간과 관리 할당이다. WAN 지연·실제 플레이 FPS·GPU/상주 메모리 측정으로 해석하지 않는다.

검증 기록과 로컬/미검증 범위는 별도 결과 보고서를 따른다. 인터넷의 서로 다른 PC/공유기 환경이나 원격 CI를 로컬 loopback 결과만으로 검증했다고 주장하지 않는다.

실행 취소·다시 실행은 싱글플레이에서 지원한다. 멀티플레이에서는 다른 참가자의 편집·수량과 충돌하지 않도록 사용하지 않으며, 세션 전환 때 기존 편집 이력을 비운다.
